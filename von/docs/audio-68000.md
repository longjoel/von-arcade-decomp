# 68000 sound program (`epr-18670.31`)

Working notebook for the audio CPU. Static evidence from the listing
`von/build/disasm/vonj-audio.lst`, regenerated with:

```sh
./bin/vonctl disasm audio
```

The recipe runs `von/tools/extract_audio.py` and `mame/unidasm -arch m68000
-basepc 0x600000`. Confidence tags follow the project convention.

## Load and memory map (KNOWN)

`epr-18670.31` is a 512 KiB 8-bit EPROM that MAME loads into the `audiocpu`
region as `ROM_LOAD16_WORD_SWAP` at `0x600000-0x67ffff`. The CPU-visible image
is therefore the per-16-bit-word byte swap of the dump; `extract_audio.py`
performs the swap and validates the reset vector.

68k program map (from `model2_state::model2_snd`):

| range | owner |
| --- | --- |
| `0x000000-0x07ffff` | sound RAM, shared with the SCSP |
| `0x100000-0x100fff` | SCSP registers (`A5` in the code) |
| `0x400000-0x400001` | sound control / IRQ mask register |
| `0x600000-0x67ffff` | this program ROM |
| `0x800000-0x9fffff` | sample ROM |
| `0xa00000-0xdfffff`, `0xe00000-0xffffff` | sample banks 4/5 |

Reset vector: SSP `0x00005000`, PC `0x00601200`. The initial `A6` is
`0x1000`, a RAM base for the driver's channel/voice state (addressing such as
`($1404,A6)` = `0x2404`, `($1800,A6)` = `0x2800`).

## Reset and initialization (`0x601200`-`0x601336`) (KNOWN)

- `0x601200`: `move #$2700,SR`, mask interrupts, write `0x3f` to the sound
  control register `0x400001`, clear D0-D7/A0-A6.
- `0x601236`: `A5 = 0x100000` (SCSP).
- `0x601240`-`0x601278`: clear RAM from `0x0000`.
- `0x601284`: SCSP init + a RAM test loop at `0x60128e`.
- `0x6012ac`-`0x6012d4`: run eleven init routines
  (`0x60133a`, `0x601390`, `0x60141e`, `0x601434`, `0x601568`, `0x60158a`,
  `0x6015bc`, `0x6015dc`, `0x60165c`, `0x601680`, `0x601696`).
- `0x601336`: `jmp $6041ea` — the engine main loop.

The initialization reads a pointer block at `0x608000`:

| word address | value | consumer |
| --- | ---: | --- |
| `0x608000` | `0x0060a010` | — |
| `0x608004` | `0x0060b5e0` | sequence table (`0x60165c`, `0x602806`) |
| `0x608008` | `0x00609da8` | voice/sample assignment table (`0x601696`) |
| `0x60800c` | `0x006080e2` | `0x601434` |
| `0x608010` | `0x00608080` | `0x6014ba` |
| `0x608018` | `0x00609884` | `0x601398` (copied to SCSP `0x100700`) |
| `0x60801c` | `0x0060ca1a` | sequence-table end (`0x60165c`) |
| `0x608028` | `0x0060d966` | byte-indexed table (`0x601b0c`) |

`0x60165c` copies the sequence table `[0x608004]` (`0x60b5e0`, length
`[0x60801c]-[0x608004]` = `0x143a`) to sound RAM `0x9000`; the engine then
indexes the RAM copy (`lea $9000.l,A2` at `0x601b28`). `0x601696` builds 16
voice records at `A6+0x1600` from `[0x608008]`, selecting each entry with a
byte from the 16-byte header at `-0x10` before the table.

## Sequence/command parser (`0x603da2`, `0x603dbc`) (KNOWN)

`0x603da2` is the per-channel packet tick. If bit 7 of `(A2)` is set it
decrements the countdown at `(2,A2)`; when that reaches zero it loads the
stream pointer `A3 = (4,A2)` and falls into the dispatcher.

`0x603dbc` dispatches on the command byte's high nibble:

```text
603dbc  move.l A3,D0
603dbe  bmi    $603ff6        ; stream pointer flag (0xff/0x80 control words)
603dc2  bclr   #0,(A2)
603dc8  move.b (A3)+,D2
603dda  andi.l #$f0,D1        ; high nibble
603de0  lsr.b  #2,D1
603de2  lea    (4,PC,D1.w),A0 ; table at 0x603de8, 16 entries
603de6  jmp    (A0)
```

Table `0x603de8`, indexed by `(high nibble) >> 2` = byte offset `0x00..0x3c`:

| command nibble | handler | shape |
| --- | --- | --- |
| `0x00`-`0x70`, `0x90`, `0xe0` | `0x603f0c` | command + two payload bytes |
| `0x80` | `0x603ede` | command + one payload byte + fixed `0x7f` |
| `0xa0` | `0x603e28` | host command: combines the next byte into a 16-bit value; `HH==0` → `0x603e98`, `HH==1` → `0x603e38`, else `0x603e6e` |
| `0xb0` | `0x603eb0` | command + two payload bytes |
| `0xc0`, `0xd0` | `0x603f38` | command + one payload byte + fixed `0x00` |
| `0xf0` | `0x603f66` | control words `0xf7` (skip), `0xf0` (seek), `0xff` (loop/end) |

Every handler writes the consumed bytes into a 1024-byte ring at `A6+0x100`
(`0x1100`), advancing the write pointer at `A6+0x1404` (`0x2404`) in 4-byte
slots and the count at `A6+0x1406` (`0x2406`). `0x603fbc` then reads the
2-byte inter-packet wait (`(2,A2)`), so a stream is
`[packet…][wait][packet…]`.

## Host command packet `ae HH LL` and the command table (KNOWN)

The i960 producer (`recovered_audio_command_bytes` in
`recovered_audio_queue.c`) frames a 16-bit command as `0xae, high, low`.
`0x603e28` is the nibble-`a` handler: it forms `0xae00 | HH` (`lsl.w #8`
then `move.b (A3)+`), branches on `HH` (`0`/`1`/other), and for `HH >= 2`
takes `0x603e6e`, which buffers the command word and the final byte into the
engine ring. Every game ID is `0x10xx`-`0x13xx`, so `HH >= 0x10` and the
three bytes pass through to the engine with the 16-bit ID in the last two
bytes. The engine's main loop (`0x601a20`) routes the high nibble `0xa` to
`0x6034b8`, the host command resolver that consumes the `HH` and `LL` bytes
directly.

### Two-level command table (`0x6034b8`)

`0x6034b8` reads `HH`; for `0x10 <= HH < 0x70` it indexes a two-level table
rooted at the pointer `[0x60801c]` (value `0x60ca1a`, immediately after the
relocated sequence table):

```text
A4 = [0x60801c] + u16([0x60801c] + 2 + (HH-0x10)*2)   ; first level
A2 = [0x60801c] + u16(A4 + 2 + LL*2)                   ; second level
control = (A2)
```

Both offset sets are relative to `[0x60801c]`. The first level has exactly
four sub-tables, matching the game vocabulary:

| `HH` | `max LL` | family |
| ---: | ---: | --- |
| `0x10` | 34 | 68000 shell BGM/select/start/win/lose (`SDB_*`) |
| `0x11` | 91 | effects and announcer voices (`SDE_*`) |
| `0x12` | 79 | per-mech weapon/attack effects |
| `0x13` | 102 | voices, round calls, music shell |

The control byte selects the path:

- `control == 0x00` (`0x10xx`, 35 commands): `0x603518` takes the sequence
  path. `A2+3` is a 32-bit sequence pointer into the sample region
  (`0x80a000` for the BGM records), and the 32-byte record that follows is a
  pointer list terminated by `0xfffffff1`.
- `control & 0x80` (`0x11xx`-`0x13xx`, 252 commands): `0x6035a0` takes the
  one-shot voice path and queues the inline stream at `A2+1`. Each entry is
  an 8-byte record `80 OP SAMPLE PARAM 00 ff 2f 00`. The `OP SAMPLE PARAM`
  packet is stored into the shared command queue, where `OP` is
  `0x9a`/`0x9b`/`0x9c` (sample bank) and `SAMPLE` is the 68000 sample/voice
  index (the 68k loop itself does not consume nibble `9`, so the packet is
  keyed by the downstream SCSP/DSP voice path):

| command | name | op | sample | param |
| --- | --- | ---: | ---: | ---: |
| `0x1101` | `SDE_bom_01` | `0x9a` | `0x01` | `0x7a` |
| `0x1115` | `SDE_hit_13` | `0x9a` | `0x15` | `0x7a` |
| `0x1200` | `SDE_tem_rifle` | `0x9b` | `0x27` | `0x7a` |
| `0x1227` | `SDE_new_hit4` | `0x9b` | `0x4e` | `0x7a` |
| `0x134b` | `SDE_new_voice5` | `0x9c` | `0x42` | `0x7f` |
| `0x1350` | `SDE_new_voice10` | `0x9c` | `0x47` | `0x7f` |
| `0x1363` | `SDE_click_0` | `0x9a` | `0x5b` | `0x73` |

For `0x11xx` the sample index equals `LL`; `0x12xx` is offset by `0x27`
(`0x1200 -> 0x27`); `0x13xx` equals `LL` again but with bank `0x9c`. The
`0x1363` click is a `0x9a` entry inside the `0x13` sub-table, so the opcode
is per-entry rather than per-`HH`.

The extracted map is `von/audio-command-map.json`
(`extract_audio_command_map.py`, `test_audio_command_map.py`): 310 commands,
all 287 named i960 IDs resolved.

## Sample descriptor table and upload (KNOWN)

The One-shot sample packets name a 68000 sample index in the current bank
(`0x9a`/`0x9b`/`0x9c`). The actual PCM comes from a 16-byte-record descriptor
table at `0x60a012`, pointed to by the word at `0x608000` (`0x60a010`; the
first word `0x15af` sizes the copy):

| offset | meaning |
| --- | --- |
| `+0x00` | u32 source pointer into the 8 MiB sample region (`0x800000+`) |
| `+0x04` | u32 copy length in bytes, minus one |
| `+0x08` | u32 end pointer, or `end-src` when `+0x0c` is nonzero |
| `+0x0c` | u32 loop/format flag |

The init path `0x6015dc` copies the whole blob to sound RAM `0x5000` and then
walks the eager-upload index list at `[0x608020]` (`0x60b5c2`); on this ROM
that list is terminated immediately (`0xffff`), so samples are uploaded
lazily. The lazy loader runs from `0x602146`:

- the low bit-31 of the source pointer means "already resident"; otherwise
  `0x602152` treats `+0` as a ROM source and `+4` as the copy length;
- `0x60216e` forms the SCSP sample address from the voice record page byte
  (`page << 12`) and writes `0x1030 | page` to the slot control word;
- `0x6021a4` copies the source into sound RAM in 0x20-byte units;
- `0x602264` stores the source and destination back into the voice record and
  keys the slot (`ori #$18,(A5,D4)` then `move.b #$80,(A3,D4)`).

The static table is extracted as `von/audio-sample-descriptors.json`
(`extract_audio_sample_table.py`, `test_audio_sample_table.py`): 347
descriptors, all with sources inside the sample region. `--extract DIR`
dumps each descriptor to a PCM8 WAV for auditioning (e.g. descriptor `0x15`
is 51,647 bytes with a 37,786-byte loop; descriptor `0x47` is 1,331 bytes).

### Sample index -> descriptor index (RESOLVED)

The `0x9a` handler `0x601af8` searches a per-track range table inside the
relocated sequence record: `0x601b48` reads a low/high byte pair and strides
12-byte entries to the matching sample index. The selected entry's first word
becomes the voice field used as the descriptor index (`0x6020c2` ->
`0x602146`).

The channel/track assignment is static. The low nibble of the packet opcode
matches a record in the effect-channel table at `0x608081`; its `+2` field is
the track index:

| opcode low nibble | track | sample range |
| ---: | ---: | --- |
| `0xa` (`0x8a`/`0x9a`) | `0x39` | `0x00..0x5e` |
| `0xb` (`0x8b`/`0x9b`) | `0x3a` | `0x27..0x7f` |
| `0xc`-`0xf` (`0x9c`+) | `0x3b` | `0x00..0x55` |

The range tables are irregular (some entries are `0xffff`), so each
`(track, sample)` is read from `0x60b5e0 + offset[track] + 4 +
(sample-lo)*12`. Joining this with the descriptor table resolves the whole
chain. Extracted as `von/audio-clip-map.json`
(`extract_audio_clip_map.py`, `test_audio_clip_map.py`): **275 commands, 0
unresolved**. Examples:

| command | name | track | descriptor | source | length |
| --- | --- | ---: | ---: | ---: | ---: |
| `0x1101` | `SDE_bom_01` | `0x39` | `0xa1` | `0x4007dc` | 25461 |
| `0x1115` | `SDE_hit_13` | `0x39` | `0xb5` | `0x468b84` | 37381 |
| `0x1200` | `SDE_tem_rifle` | `0x3a` | `0xc2` | `0x4cebb6` | 12299 |
| `0x134b` | `SDE_new_voice5` | `0x3b` | `0x142` | `0x759e64` | 16385 |
| `0x1350` | `SDE_new_voice10` | `0x3b` | `0x147` | `0x76f0a2` | 26213 |
| `0x1363` | `SDE_click_0` | `0x39` | `0xeb` | `0x5fee7e` | 1101 |

`--extract DIR` writes a PCM8 WAV per command for auditioning. The
`command -> effect track -> descriptor -> clip` chain is therefore complete
for all one-shot (SFX/voice) commands. The seven `0x8a` entries
(`0x1122`, `0x1123`, `0x1146`, `0x1147`, `0x1155`, `0x1157`, `0x115a`) are
unnamed but resolve through the same `0xa` track.

## Sound-effect trigger map (KNOWN conditions)

Resolved by disassembling the producers of the shared effect IDs. All
conditions are on i960 object fields; the IDs are the host commands from
`von/audio-command-map.json`.

### Weapon fire (per-fighter / per-move)

- Profile weapon field `+0x488/+0x48c` read at the `object+0x1ab` gate
  (`0x34d9c`, `0x34dac`) - per-mech primary weapon (`SDE_tem_rifle`,
  `SDE_rai_baz`, ...).
- The `0x12xx` move-script clusters (`0x4b264..0x67c50`) select fixed
  per-weapon IDs and store them to `object+0x1fc`
  (`SDE_2_tem_sword_on/hit/cut/off`, `SDE_2_vip_sevenway`, ...).

### Movement

- Jump/air: profile `+0x490/+0x494` at states 22, 35, 37
  (`SDE_jump_01/02/03`).
- Dash loop / move-end: profile `+0x498/+0x4a0` and `+0x49c/+0x4a4` at the
  `object+0x196` locomotion toggle (`0x34300`/`0x34354`).

### Impact / contact (`SDE_hit_13` = `0x1115`, 25 sites)

The effect/hit update family indexes the per-effect-type table at `0xc4f40`
by the effect's type byte `(A0)+0`. The per-type handlers
(`0xbf3e0..0xc20f0`) play `SDE_hit_13` when the state word `+4` hits
`table[type] - 2`:

```text
0xbf624  g5 = ldob (A0)              ; effect type
0xbf62c  g5 = ldis 0xc4f40[g5*8]     ; per-type threshold
0xbf620  g4 = ldos 0x4(A0)           ; effect state
0xbf638  g5 = g5 - 2
0xbf63c  if (g4 != g5) return
0xbf640  play 0x1115 (SDE_hit_13)
```

The shared effect-frame helper `0xbf2f0` uses the same table one step
earlier (`+4 == table` or `table-1`) to emit the impact visual (geometry
packet) via `0xbf32c`. So `SDE_hit_13` is the generic projectile/effect
**impact** sound at the hit frame, not tied to a specific button or weapon.
The geometry-handler family in table `0x41c50` (`0x3ff80`, `0x400f0`,
`0x40270`, `0x406cc`, `0x41340`, `0x414b0`, `0x419c0`, dispatched from
`0x41f20`) fires it the same way via `0x3eca0[type] - 2 == state`.
`SDE_hit_03` (`0x1113`) fires at `0x4202c` in `0x41f20`; `SDE_hit_4_rev`
(`0x111e`) at `0x2ac18`.

### Explosion / destruction (`SDE_bom_*`)

The object runtime handlers in table `0x41c50` (`0x3f8d0`, `0x3fa90`,
`0x3fc50`, `0x3fdc0`, ...) drive a per-type lifetime countdown at `+2` and
play explosion stages:

```text
0x3f960  g5 = ldos 0x2(A0)              ; countdown +2
0x3f968  g4 = ldos 0x3eca0[type*2]      ; per-type lifetime
0x3f980  if (g5 == g4 - 2) -> play 0x1101 (SDE_bom_01)
0x3f9c4  if (g5 == g4 - 5) -> play 0x1102 (SDE_bom_02)
```

The `0x3fdc0` variant fires `0x1105`/`0x1101` (`SDE_bom_11`) at
`g4-2`/`g4-3`; the `0x3fec8`/`0x3fd10` variants likewise select the
`bom_*` pair by object variant. So the `SDE_bom_*` IDs are the **object
destruction/explosion stage sounds**, keyed to the per-type lifetime table
`0x3eca0` and the current countdown, not to a player action.
`SDE_bom_new1/3` (`0x1120`/`0x1121`) are separate effect families
(`0x3e5dc`, `0x9f45c`, `0xa3f6c`, `0xb0b10`, `0xbc07c`, `0xd4c80`).

### Beam / weapon sustain

`SDE_beam_03`/`SDE_2_beam_03`/`SDE_2_beam_07` (`0x110b`/`0x112f`/`0x1132`)
fire from the effect-frame handlers `0xd7814`, `0x3984c`, and `0x39360`,
which are reached from the weapon/effect update loop rather than the
move-script launch path.

### Announcer / stage

`SDE_type_05` (`0x1111`) is the play-setup/state voice; `SDE_count_down`,
`SDE_siren`, `SDE_new_siren` are the round timer; `SDE_round_NN`,
`SDE_new_voice*`, and `SDE_voice_*` are the announcer calls selected by the
`0x195e0`/`0x21180` tables; `SDE_click_*` are UI.

## Engine loop and voice allocator (KNOWN structure)

- `0x6041ea` is the main engine loop entry. It reads a byte from `(A0)` and
  branches; `0x601a20` is a per-frame tick that walks channel records.
- `0x601aa6` dispatches on the high nibble of `($140e,A6)` through the 16-entry
  table at `0x601ab6`. Index `0x28` (`nibble 0xa`) jumps to `0x6027f0`, the
  sequence/voice allocator.
- `0x6027f0` reads a stream byte, uses `(2,A0)` as an index into the
  relocated sequence table, stores pitch/level state (`($1415,A6)`,
  `($1416,A6)`), then scans 32 voice slots at `A6+0x1800` and triggers a free
  one through `0x6028e8`.
- `0x605be4` is a 128-byte byte table used to seed a per-voice field.

## Per-voice pitch and gain (RESOLVED)

The `0x9a` sample path programs the SCSP from the track entry (12 bytes at
`0x60b5e0 + offset[track] + 4 + (sample-lo)*12`):

- `entry+2` is the note field. `0x602710` decodes it to the SCSP pitch
  register (`OCT` in bits 11-14, `FNS` in bits 0-9) through the FNS table at
  `0x605ca4`; the playback rate is `Step()/4096` with
  `octave=(OCT^8)-6`, `Fn=(FNS+1024)<<octave` (MAME's `scsp_device::Step`).
- `entry+4` is the slot `data[0xb]` high byte: `DISDL` (bits 5-7) and `DIPAN`
  (bits 0-4). The path clears `TL` (`entry+4` only sets the direct-send
  level).

Baked levels use MAME's pan-table model `4 * TL * fSDL(DISDL)` with
`SDLT = (-inf,-36,-30,-24,-18,-12,-6,0)` dB, so most effects land at
`-12 dB` and the announcer voices at `-6 dB`. Cross-check: the decoded
`OCT`/`FNS` for the effect tracks (e.g. `OCT 14/FNS 0x0157` and
`OCT 15/FNS 0x0000`) match the key-on `K` lines captured from the original at
runtime.

`entry+8` is the EG register pair written to `data[4]`/`data[5]`. All 528
effect/voice entries use `AR=31, D1R=0, D2R=0, DL=0, RR=31`: a single EG
attack ramp of `ARTimes[31] = 55 ms` (MAME's `m_EG_TABLE` curve
`10^(3*(i-0x3ff)/32/20)`), then a hold (D1R/D2R infinite), with release only
on key-off (which a one-shot never reaches, since it stops at the sample end).

`extract_audio_clip_map.py` stores `pitch_scale`, `gain_db`, `octave`, `fns`,
`disdl`, `dipan`, `ar`, `d1r`, `d2r`, `dl`, `rr`, and `attack_ms` per command
in `von/audio-clip-map.json`; `export_audio_manifest.py` bakes
`pitch`/`gain_db`/`pan` into the Godot manifest and applies the 55 ms EG
attack to each clip WAV, and `VonAudio` applies pitch and volume. `DIPAN` is
carried for a future stereo panner (the current pool is mono).

## Kernel and Godot integration

The sound decision lives in the i960 game logic (the action/effect handlers),
not in the 68000. The port therefore keeps the kernel emitting command IDs and
replaces the 68000/SCSP with a static clip table and a host player:

- `von-godot/native/kernels/von_recovered_kernel.c` records the decoded IDs
  (`rv_audio_emit`) at the jump, dash start/stop, weapon-fire, impact, and
  round-end transitions; the mock kernel emits synthetic cues.
- The kernel ABI is v7: `VonRenderSnapshot.sound_events[]` carries the most
  recent window with a monotonic `sequence`, so the host drains the delta.
- `von-godot/scripts/match_session.gd` filters fresh events and
  `von-godot/scripts/von_audio.gd` plays them from a 24-voice pool using
  `assets/generated/audio/audio_clips.json`.
- `von/tools/export_audio_manifest.py` (`./vonctl export audio`) stages the
  manifest and 275 PCM16 clips from the sample ROM into the Godot tree.

The `ae HH LL` byte framing is an internal event ID only; nothing emulates the
68000 command parser or the SCSP voice engine.

### Offline BGM renders

The game's BGM is **DSP/RAM driven** (the 68000 writes almost no SCSP
registers during music), so static sequence decoding is not needed. Instead
`von-godot/native/scsp` is a standalone bit-exact port of MAME's YMF292-F that
replays a register trace plus a sound-RAM write trace. The traces come from
two small MAME hooks (restored under `third_party/patches/004{5,6}`); the
Lua-only RAM tap segfaults MAME.

The select and attract tracks are rendered and verified against a MAME
`-wavwrite` reference at r>0.99 with unity gain
(`von-godot/scripts/render_scsp_audio.sh`), staged as `music_select.wav` /
`music_attract.wav`, and mapped to `SDB_select*` / `SDB_title`/`SDB_demo` in
the Godot manifest.

All ten arena BGMs are rendered the same way with
`von/tools/probe_stage_binding.lua`, which joins the deterministic first match
and forces the stage-ordinal cells `0x503a80`/`0x509b80` to
